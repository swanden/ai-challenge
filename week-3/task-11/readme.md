## Что есть каждый слой (с уточнениями из обсуждения курса)

| Слой | Что это | Хранилище | В запрос |
|------|---------|-----------|----------|
| **short-term** | текущий **диалог** — сообщения чата | `short-term.json` | `messages` |
| **working** | **TaskContext** — данные **задачи**: план, что сделано, текущий шаг, решения | `working.json` | `System` |
| **long-term** | профиль / решения / знания | `long-term.md` (правится руками) | `System` |

Три важных уточнения, которые часто путают:

**Рабочая память — это НЕ текущий диалог.** Диалог лежит в short-term. Рабочая
память (TaskContext) — это **сущность, которая хранит состояние конкретной задачи**
(план, что сделано, текущий шаг, принятые решения). Она привязана к задаче, а не к
чату: задача может уложиться **в один чат** или **растянуться на несколько** — память
*про задачу* при этом одна и та же (поэтому `working.json` грузится на старте и
переживает сессии). Пример: фича = 3 сессии (бизнес-ресёрч → разработка → тесты),
память про фичу и есть рабочая; «настройки по проекту, над которым работаем» — тоже
рабочая. В мультиагентном случае она ближе к **оркестратору** — держит выводы других
агентов и общие настройки задачи.

**Долговременная — простой вариант: редактируемый `.md`.** Это профиль, durable-решения
и знания в одном markdown-файле (`long-term.md`), который можно **открыть и поправить
руками**. Грузится в System prompt. (Дальше можно усложнять: БД, векторная память.)

**Краткосрочная — просто сообщения чата** в хранилище (наш «БД» — `short-term.json`).

### Почему working — это JSON, а не авторский `.md`

Формат слоя следует за его ролью — **кто и как его ведёт**:

- **long-term.md ведёшь ты, и он стабилен.** Профиль и durable-знания меняются редко,
  это «проза», которую удобно курировать руками в markdown; агент его в основном
  читает. Поэтому редактируемый `.md` (как `CLAUDE.md`) — логично.
- **working ведёт код, и он мутирует на каждом шаге.** `MarkDone` перекладывает пункт
  из `plan` в `done`, `SetCurrent` двигает текущий шаг, `Decide` пишет решение. Это не
  текст, который сочиняют один раз, а **структура с полями**, по которым ходит код. На
  структуре (`plan []string`, `done []string`, `facts map`) такие операции — одна
  строка; на свободном markdown — хрупкий парсинг туда-обратно.

Это совпадает с лекцией: долговременную лектор назвал «простой вариант — редактируемый
`.md`», а рабочую — **TaskContext**, и на слайде это `data class TaskContext(...)`, т.е.
структура данных, а не markdown-документ. Поэтому `working.json` — структурный, а не
`.md`, который пишут руками. План при этом всё равно можно задать руками — командой
`/plan a; b; c`; дальше статус (`done`/`current`) обновляет код.

## long-term.md ты ведёшь сам

Долговременная память — это **твой** файл `long-term.md` (как `CLAUDE.md`): профиль,
durable-решения, знания. Ты его создаёшь и правишь **руками**, а агент его только
**загружает** и инжектит в System prompt. Агент **не перезаписывает** его на каждом
ходу — на ходах сохраняются только слои, которыми управляет он сам
(`short-term.json`, `working.json`). long-term.md меняется лишь по явной команде
`/know` (агент-ассистированное дополнение) или твоей правке + `/reload`.

Пример `memory/long-term.md`, который ты пишешь сам:

```markdown
# Профиль
- Роль: Senior Go-разработчик (распределённые системы)
- Стиль ответа: кратко, с рабочими примерами кода
- Язык: русский
- Ограничения: Go; минимум зависимостей

# Решения и знания
- Логи: структурный JSON
- БД по умолчанию: Postgres
```

В репозитории есть готовый образец `long-term.md` — положи его в каталог `-mem`
(по умолчанию `./memory/long-term.md`), и его подхватят и чат, и `-report`. Если файла
нет — в чате выводится подсказка создать его. `SetProfile()`/`/know` —
вспомогательные способы засеять/дописать .md из кода, не основной путь.

## Явная запись (что и куда): решает разработчик

«Вы явно выбираете, что и куда сохраняется» — **вы = разработчик**: маршрутизация
делается в коде («под капотом»), явными методами. Опционально можно дать выбор и
пользователю — в этом проекте это команды чата (`/task`, `/decide`, `/know` …),
но основной механизм — вызовы из кода:

```go
mem.Dialog(role, text)            // → short-term  (диалог; пишет агент сам)
mem.SetTask(name, goal)           // → working     (TaskContext: задача/цель)
mem.SetPlan("a","b","c")          // → working     (план)
mem.MarkDone("a"); mem.SetCurrent("b") // → working (статус: сделано/текущий шаг)
mem.Decide("база","Postgres")     // → working     (решение по задаче)
mem.SetProfile(profile)           // → long-term.md (профиль)
mem.AppendKnowledge("логи в JSON")// → long-term.md (durable знание/решение)
mem.ResetTask()                   // очистить working, не трогая остальное
```

## Явный выбор слоёв в запросе (policy)

Под задачу слои включаются/выключаются (лектор: где-то не нужен профиль, где-то
не нужна history — пропускаете). long-term и working → `System`, диалог → `messages`:

```go
type Policy struct {
Profile    bool // long-term (.md)
Working    bool // working (TaskContext)
ShortTermN int  // сколько последних реплик диалога взять
}
system, msgs, used := mem.Build(query, Policy{Profile: true, Working: true})
```

### Как слои подмешиваются в запрос

Лектор подтвердил: рабочая и долговременная память **подмешиваются в системный
промпт**, а диалог уходит обычными сообщениями. У нас в `Build` это разложено так:

| Слой | Куда в запросе | Как именно |
|------|----------------|------------|
| **long-term** (`long-term.md`) | `System` | отдельным блоком `[ДОЛГОВРЕМЕННАЯ ПАМЯТЬ — profile.md]` |
| **working** (TaskContext) | `System` | отдельным блоком `[РАБОЧАЯ ПАМЯТЬ — TaskContext]` |
| **short-term** (диалог) | `messages` | реплики как `user`/`assistant` + сам запрос последним |

То есть System prompt собирается из 1–2 блоков памяти (профиль и/или задача — что
включено политикой), а краткосрочный диалог идёт штатными сообщениями. Какие слои в
итоге попали в System, видно в выводе `-report` в строке «Слои в запросе».

Почему так: профиль и состояние задачи — это **контекст-инструкция** «кто ты и над
чем работаем», ей место в System; а диалог — это сама переписка, её естественно
передавать сообщениями. Это и есть «подмешивание» памяти в системный промпт.

## Два режима

### Демонстрация

```bash
go run . -report                 # рабочий прогон + сохранение слоёв в ./memory
go run . -report -mem ./profileA # тот же прогон с другим каталогом памяти
```

`-report` делает реальный прогон (вопрос под политиками A→C через API) и затем
**сохраняет все три слоя в файлы памяти** каталога `-mem` (по умолчанию `./memory`):
`short-term.json`, `working.json` и `long-term.md`. Долговременный слой при этом
**ориентируется на твой `long-term.md`**, если он лежит в каталоге: его отчёт
использует и **не перезаписывает**; если файла нет — берёт демо-профиль и пишет его
как образец. То есть после `-report` в `./memory` лежат заполненные файлы памяти.

(1) Какие данные попадают в каждый слой — разработчик **в коде** явно маршрутизирует
каждый вход в свой слой (+ дамп слоёв и оговорка, что working ≠ диалог). (2) Как память влияет на ответ — один вопрос под
политиками A→C.

### Интерактивный чат (память раздельно на диске)

```bash
go run . -mem ./memory
```

Команды: `/know <текст>` и `/reload` (long-term.md), `/task`, `/goal`, `/plan a; b`,
`/current`, `/done`, `/decide k=v` (working), `/mem`, `/reset-task`, `exit`.
long-term.md можно править руками и подхватить через `/reload`.

В чате файлы слоёв создаются и обновляются автоматически (после каждого хода и на
`exit`) в каталоге `-mem`:

```
memory/
  short-term.json   # диалог
  working.json      # TaskContext
  long-term.md      # профиль/знания (правится руками)
```

```
# Часть 1. Какие данные попадают в каждый слой
Маршрутизируем входные данные ЯВНО — каждый факт в свой слой:

  → [long-term (.md)] профиль + durable-решение → long-term.md
  → [working (TaskContext)] задача/план/статус/решения → working (TaskContext)

Важно: рабочая память (TaskContext) — это НЕ текущий диалог. Диалог лежит

Состояние памяти по слоям:

  long-term (.md) — 180 символов markdown
      # Профиль
      - Роль: Senior Go-разработчик (распределённые системы)
      - Стиль ответа: кратко, с рабочими примерами кода
      - Язык: русский
      - Ограничения: Go; минимум зависимостей
      - Предпочтение: структурные логи в JSON

# Часть 2. Как память влияет на ответ ассистента
Один и тот же вопрос: "Подскажи, как организовать конфигурацию для нашего сервиса?"

## (A) без памяти (stateless)
Слои в запросе: нет (stateless)
Ответ: Общий совет: вынесите конфиг в ENV или YAML, читайте при старте,

## (B) + long-term (.md профиль/знания)
Слои в запросе: long-term (.md)
Ответ: Для Go без лишних зависимостей: struct Config, чтение из ENV, парсинг

Слои в запросе: long-term (.md), working (TaskContext)
Ответ: Для order-svc на шаге «описать конфиг»: Config со строкой Postgres и

=== Вывод ===
• Три слоя хранятся РАЗДЕЛЬНО и в разных форматах: диалог → short-term.json,
  TaskContext → working.json, профиль/знания → long-term.md (правится руками).
• В каждый слой пишем ЯВНО; в запрос слои подставляем ПО ПОЛИТИКЕ.
• Влияние: без памяти — общий совет; +long-term — под senior/Go; +working —
  конкретно по задаче order-svc (Postgres/Kafka, текущий шаг).
```

## Файлы

- `memory.go` — три слоя (short-term / working=TaskContext / long-term=.md),
  явная запись, `Policy`, раздельное хранение, `Inspect()`.
- `agent.go` — агент: собирает запрос из выбранных слоёв, диалог → short-term.
- `usage.go` — тарифы по моделям, типы сообщений.
- `report.go` — маршрутизация по слоям + влияние слоёв на ответ.
- `main.go` — `-report` либо чат с командами записи в слои.

## Где создаётся `memory/`

По умолчанию каталог памяти — **рядом с кодом задачи** (`week-3/task-11/memory`), а не
в текущей директории. Это сделано через `defaultMemDir()` (`runtime.Caller`), поэтому
команда из корня репозитория

```bash
go run ./week-3/task-11 -report
```

создаёт `memory/` внутри `week-3/task-11/`, а не в корне. Переопределить путь можно
флагом `-mem`, например `-mem ./week-3/task-11/memory` или любой свой каталог.
