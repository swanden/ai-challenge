## Что нового по сравнению с днём 11

День 11 дал три слоя памяти: **short-term** (диалог), **working** (TaskContext),
**long-term** (.md). День 12 надстраивает **персонализацию**: долговременный слой
теперь = **активный профиль**, и профилей несколько (между ними переключаемся).

| Слой | Что хранит | В запрос |
|------|-----------|----------|
| short-term | диалог | `messages` |
| working | TaskContext (план/сделано/шаг/решения) | `System` |
| **long-term** | **активный профиль** (стиль/формат/ограничения) | `System` |

То есть профиль не отдельная «фича сбоку», а **долговременный слой памяти агента** —
он подмешивается в System каждого запроса вместе с working и диалогом.

## Профили

- Профиль = редактируемый markdown (`profiles/<id>.md`). Несколько профилей,
  хранятся раздельно. Встроенные: `none` / `junior` / `senior-go`; плюс свои `.md`.
- Выбор профиля → его содержимое становится долговременным слоем
  (`agent.SetProfile(p)` → `mem.SetLongDoc(p.Doc)`).
- Подключение к каждому запросу: профиль уходит в System автоматически (видно в
  строке «слои» после ответа).

```
profiles/                 memory/
  junior.md                 short-term.json   (диалог)
  senior-go.md              working.json      (TaskContext)
  <твой>.md               # long-term = активный профиль (из profiles/)
```

Профиль персистит `ProfileStore` (каталог `profiles/`); диалог и TaskContext —
память агента (каталог `memory/`). Долговременный слой отдельно в `memory/` не
дублируется — он приходит из выбранного профиля.

## Два режима

### Демонстрация

```bash
go run ./week-3/task-12 -report
```

Отчёт показывает **только задание текущего дня** — персонализацию: один вопрос
(«Объясни dependency injection…») прогоняется через `none` / `junior` / `senior-go`,
видно, как ответ меняется под профиль (слайды 10 и 16), и что профиль подмешивается
автоматически. Память (working/диалог) в отчёт дня 12 не выносится — она остаётся в
агенте и используется в чате (`/mem`, `/task`, …). Принцип: **агент накапливает
функционал, но `-report` демонстрирует задание только текущего дня.**

### Чат

```bash
go run ./week-3/task-12                  # профиль senior-go по умолчанию
go run ./week-3/task-12 -profile junior
```

Команды:
- профиль (long-term): `/profile <id>`, `/profiles`, `/whoami`
- working: `/task`, `/goal`, `/plan a; b`, `/current`, `/done`, `/decide k=v`
- прочее: `/mem` (показать все слои), `/reset-task`, `exit`

Каталоги `memory/` и `profiles/` по умолчанию — рядом с кодом задачи
(`week-3/task-12/...`), переопределяются флагами `-mem` / `-profiles`.

## Вывод по заданию и прогону

**Задание выполнено.** Создан профиль пользователя (несколько: `none`/`junior`/`senior-go`,
каждый — свой `.md` с предпочтениями: стиль, формат, ограничения). Профиль подключается
к **каждому** запросу автоматически — подмешивается в System (в выводе `Профиль в запросе:
true`), пользователь не указывает его в самом вопросе.

**Прогон подтвердил персонализацию.** Один и тот же вопрос про dependency injection дал
три разных ответа под профиль:
- `none` — нейтральное «учебниковое» объяснение через аналогию;
- `junior` — дружелюбно, простыми словами, с эмодзи и разбором «что такое зависимость»;
- `senior-go` — сразу к сути, идиоматичный Go с интерфейсами и конструкторами, без воды.

Это ровно то, что требовали проверки задания: «ответы для разных профилей» и «что
ассистент учитывает автоматически».

**Накопительность.** Память дня 11 (3 слоя) осталась в агенте и работает в чате
(`/mem`, `/task`, …); профиль встроен как долговременный слой. При этом `-report`
показывает только задание дня 12 — персонализацию.

**Нюанс прогона:** у `none` и `junior` ответ упёрся в `MaxTokens=1024` (`out=1024`,
обрезано). На демонстрацию различий профилей это не влияет; для полных ответов можно
поднять `maxTokens` в `agent.go`.
