# День 34. Ассистент для работы с файлами проекта

Это тридцать четвёртый день и последнее структурированное задание курса (день 35 — уже свободная
«реальная задача» на выбор). Как и всю неделю, я продолжаю накопительный агент: каталог
`week-7/task-34/` — это копия вчерашнего `task-33/` с одной новой возможностью. В этот раз я
сделал ассистента, который не просто отвечает текстом, а сам работает с файлами проекта: читает
их, анализирует и — если нужно — создаёт или меняет.

Здесь есть принципиальное отличие от всех предыдущих дней недели, и именно оно определило
устройство решения. До сих пор каждый наш MCP-сервер был либо только на чтение (git в дне 31,
CRM в дне 33), либо писал в свою изолированную песочницу (заметки в дне 20). В этот день ассистент
впервые по-настоящему меняет файлы самого проекта. Поэтому впервые за неделю понадобился настоящий
механизм подтверждения перед опасной операцией — тот самый human-in-the-loop, которого требовала
лекция недели и который мы до сих пор осознанно обходили, делая все серверы доступными только на
чтение. В этот день такой механизм наконец уместен, а не искусственен.

## Что говорит курс (разбор чата)

Челлендж на этой неделе завершается, и в чате это чувствовалось: вышло финальное видео,
опубликованы сразу и день 34, и день 35, разосланы ссылки на продвинутые потоки. Дедлайн для
переноса — понедельник.

Из обсуждения я вынес одну важную для этого дня мысль. Участник Писаков высказал претензию, что
задания недели в сумме собираются в «свой claude code на минималках, который выбросят после
челленджа». Файловый ассистент — это буквально то, о чём он говорил, и претензия справедлива. Но
у нашего решения есть чем на неё ответить: во-первых, ассистент работает по нашему же проекту и
переиспользует все наработки недели (пять MCP-серверов, RAG, механизм генерации); во-вторых, и это
главное, он показывает гейт подтверждения перед записью — то, чего наивная реализация «в лоб»
обычно не делает. Именно этот гейт и есть содержательная часть дня, а не сам факт записи файла.

## Решение

### Задача ставится целью, а не командой «открой файл X»

Задание прямо требует, чтобы ассистент сам инициировал работу с файлами. Поэтому пользователь
задаёт цель словами — «обнови changelog» или «проверь инварианты», — а какие файлы прочитать, что
в них проанализировать и что записать, ассистент решает сам. Пользователь ни разу не называет
конкретный путь к файлу.

### Два сценария

Задание просит минимум два сценария, и я выбрал два, которые естественно ложатся на уже готовые
части агента.

Первый сценарий — **сборка changelog из истории git**. Ассистент сам решает, что ему нужен
git-лог, и читает его через MCP-сервер git (тот самый, что появился в дне 31). Затем модель
превращает сырой список коммитов в аккуратный markdown-changelog, сгруппированный по смыслу.
Здесь ассистент работает с двумя файлами: читает историю git и существующий `CHANGELOG.md` (если
он есть), а на выходе предлагает обновлённый `CHANGELOG.md`. Это пример сценария «сгенерировать
новый файл» из задания.

Второй сценарий — **проверка файлов на инварианты**. Ассистент сам находит `.go`-файлы верхнего
уровня проекта, проверяет каждый на набор простых правил (не использовать `panic()` в обычном
коде, не оставлять `TODO` и `FIXME` в коммите) и составляет отчёт. Отчёт он предлагает записать в
`docs/invariant-report.md`. Это пример сценария «проверить соответствие файлов правилам или
инвариантам».

Проверка правил сделана аккуратно в одном важном месте: паттерн, найденный внутри комментария или
строкового литерала, не считается нарушением. Без этого сам файл сценария (`file34.go`) ловился бы
на собственных определениях правил — ведь в нём слова `panic(` и `TODO` перечислены как строки, а
не как реальный код.

### Гейт подтверждения перед записью

Это сердце дня. Прежде чем что-либо записать, ассистент всегда показывает diff — что именно он
собирается изменить и почему. Дальше поведение зависит от режима.

По умолчанию (без флага `-apply`) ассистент работает в режиме предпросмотра: показывает diff и
ничего не пишет на диск. Это и обеспечивает воспроизводимость, которую требует задание, — прогон
можно повторять сколько угодно раз, ничего не меняя.

С флагом `-apply` включается собственно гейт: после показа diff ассистент спрашивает у человека
подтверждение `y/N` и записывает файл только при явном согласии. Любой другой ответ означает
отказ, и файл остаётся нетронутым. Это и есть human-in-the-loop из лекции: модель предлагает
изменение, но последнее слово — за человеком.

## Запуск

Подготовка такая же, как в предыдущие дни. Нужна локальная модель эмбеддингов (её поднимает
Ollama) и ключ облачной модели — облако используется в сценарии changelog, где модель
переписывает git-лог в человекочитаемый вид.

```bash
cd ~/projects/ai-challenge

ollama serve &
ollama pull nomic-embed-text
export ANTHROPIC_API_KEY=sk-ant-...
```

### Одна команда для видео

```bash
# только предпросмотр: оба сценария показывают diff, ничего не пишут
go run ./week-7/task-34 -file34

# с записью: после каждого diff ассистент спросит подтверждение y/N
go run ./week-7/task-34 -file34 -apply
```

Первая команда проходит оба сценария и показывает, что ассистент сам нашёл нужные файлы, сам
подготовил изменение и вывел diff, — при этом на диск ничего не попадает. Вторая та же, но с
включённым гейтом: на ней видно, как ассистент спрашивает разрешение перед записью и пишет файл
только после «y». Для видео достаточно записать обе.

### Интерактивный режим

```bash
go run ./week-7/task-34 -apply

> /file обнови changelog
> /file проверь инварианты
> exit
```

Здесь цель ставится словами, а ассистент сам выбирает подходящий сценарий. Флаг `-apply`,
указанный при старте, включает гейт записи; без него команда `/file` только покажет diff.

## Что проверено

В песочнице (без облака) я проверил рендер diff — и для нового файла, и для изменения
существующего, — а также сценарий проверки инвариантов на реальных 35 файлах проекта. Отдельно
проверил ту самую аккуратность с комментариями и строками: после доработки чек корректно перестал
считать нарушением слова `panic(` и `TODO`, встречающиеся в кавычках внутри самого `file34.go`, и
выдал «нарушений не найдено».

Сам гейт (ввод `y/N`) и сценарий changelog целиком проверяются только на живом запуске:
интерактивный ввод в песочнице не воспроизвести, а changelog требует облачной модели.

## Фактический прогон (на моём MacBook M3 Max)

Прогон `-file34` (режим предпросмотра) прошёл оба сценария и показал, что ассистент сам нашёл
нужные файлы и подготовил изменения. В первом сценарии он прочитал последние 15 коммитов через
git и собрал из них аккуратный changelog, сгруппированный по разделам Features / Fixes / Refactor.
Во втором — проверил 35 `.go`-файлов проекта и, не найдя нарушений, подготовил отчёт. В этом режиме
на диск ничего не записалось, только показались diff — ровно как задумано для воспроизводимости.

Прогон `-file34 -apply` показал работу гейта: перед записью ассистент показал diff и спросил
подтверждение, и по «y» файл `CHANGELOG.md` был записан (385 байт). Во втором сценарии проявилась
приятная деталь — отчёт о проверке инвариантов был записан ещё в предыдущем прогоне, его
содержимое не изменилось, и гейт корректно не стал предлагать перезапись идентичного файла:
«изменений нет — файл уже актуален, писать нечего». Это правильное поведение: ассистент не дёргает
человека подтверждением там, где писать нечего.

### Найденный дефект: второй запрос подтверждения терял ввод

Первый же прогон с `-apply` вскрыл настоящий баг, причём в самой важной части дня — в гейте. На
первый вопрос подтверждения я ответил «y», а ассистент понял это как отказ и файл не тронул. При
этом второй гейт на «y» отработал правильно. Причина оказалась в том, что на каждый вызов гейта я
создавал новый `bufio.Scanner` поверх `os.Stdin`. Scanner читает с упреждающей буферизацией, то
есть захватывает из потока больше одной строки за раз, — и первый сканер «съедал» ввод, который
предназначался второму, из-за чего один из ответов терялся. Это классическая ошибка: несколько
сканеров на одном и том же stdin.

Исправил заменой на один общий буферизированный ридер (`bufio.Reader`) на весь процесс, который
читает ввод построчно. Покрыл это тестом: два «y» подряд из одного потока теперь оба принимаются,
«n» — отказ, «да» — согласие. Урок здесь тот же, что не раз повторялся за неделю, — такой дефект
не виден при обычной сборке и проверке, его показывает только живой прогон с реальным вводом.

## Границы

Правила для проверки инвариантов намеренно простые — это поиск подстрок (`panic(`, `TODO`,
`FIXME`), а не полноценный разбор синтаксиса Go. Для демонстрации сценария этого достаточно, а в
реальном проекте эту проверку заменил бы линтер или анализ AST. Diff тоже простой, построчный, без
слияния по алгоритму Майерса, — его задача здесь показать человеку суть изменения перед записью, а
не быть точным как `git diff`.

## Связь с неделей

Этим днём агент впервые за неделю получает право менять файлы проекта, и вместе с ним — гейт
подтверждения, который лекция требовала с самого начала недели. Всю неделю мы обходились без него
честно, делая серверы доступными только на чтение, и здесь он появляется там, где действительно
нужен. При этом сам ассистент переиспользует уже готовые части: MCP-сервер git для истории
коммитов и общий механизм генерации для changelog. Это и есть содержательный ответ на претензию
про «claude code на минималках» — важна не запись файла сама по себе, а то, что она проходит через
явное подтверждение человека.
