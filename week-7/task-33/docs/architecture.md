# Архитектура агента

Накопительный CLI-агент AI Challenge. Один `package main` + библиотечный пакет `ragcore`.
Каждый день недели добавляет ровно одну возможность, не ломая предыдущие.

## Слои

Агент — это не «обёртка над API». Это шесть независимых слоёв, каждый со своей границей.

### 1. Память (`memory.go`) — три слоя

| Слой | Что хранит | Куда попадает в запросе |
|---|---|---|
| Долговременная (long-term) | активный профиль пользователя | system-блок |
| Рабочая (working) | `TaskContext`: цель, план, состояние задачи | system-блок |
| Короткая (short-term) | последние N реплик диалога | messages |

Чем именно из памяти пользоваться, решает `Policy{Profile, Working, ShortTermN}`.
`FullPolicy()` включает все три слоя. Память сериализуется в каталог `memory/`.

### 2. Профили (`profile.go`)

`ProfileStore` читает `profiles/<id>.md`. Готовые профили: `senior-go`, `junior`, `none`.
Профиль подмешивается в долговременный слой памяти и меняет стиль и глубину ответов.

### 3. Конечный автомат задачи (`state.go`, `pipeline.go`)

Детерминированный FSM, а не «модель сама решит, что дальше»:

```
planning → execution → validation → done
                ↑            │
                └────────────┘   (не прошло — назад в execution)
```

Разрешённые переходы жёстко заданы в `transitions`, у каждого этапа своё ожидаемое
действие (`expectedAction`). Модель не может перепрыгнуть этап — код не позволит.

### 4. Инварианты (`invariants.go`, `enforce.go`)

Два способа проверки ответа:

- `EnforceCode` — детерминированные стоп-слова и правила, проверяются кодом;
- `EnforceLLM` — семантическая проверка вторым вызовом модели (флаг `-llm-check`).

Нарушение → `Reply.Refused = true` и список `Violated`.

### 5. Рой ревьюеров (`swarm.go`)

`Swarm` — несколько ревьюеров с разными ролями плюс оркестратор, который сводит их
вердикты. Включается флагом `-swarm`, привязывается к этапу FSM (`-swarm-stage`).

### 6. Инструменты (`mcptools.go`) и генерация (`completer.go`)

См. отдельные разделы ниже.

## Completer — шов «облако ↔ локаль»

Все текстовые флоу агента — это один и тот же паттерн: system-промпт + сообщения → текст.
Чтобы не прибивать их к облаку, введён интерфейс:

```go
type Completer interface {
    Complete(ctx context.Context, system string, msgs []Msg, opt CompleteOpts) (string, GenUsage, error)
    Name() string
}
```

Две реализации: `cloudCompleter` (Anthropic API) и `localCompleter` (локальная модель через
Ollama). Переключение — флагом `-backend cloud|local`.

**Что идёт через `Completer`:** мини-чат (`chatAnswer`), обновление памяти задачи
(`updateTaskMemory`), рой ревьюеров, `EnforceLLM`.

**Что осознанно остаётся облачным:** MCP-цикл tool-use (`Agent.ask` завязан на формат
`tool_use`/`tool_result` SDK) и RAG-реранк/rewrite (`rerank.go`). Надёжный tool-calling на
7B-модели — отдельная задача, не решённая в рамках челленджа.

**Важное следствие (реальный баг дня 27):** порог «не знаю» и score обязаны быть в одной
шкале. С LLM-реранком score — это оценка судьи 0–10. Без реранка (локальный режим) score —
косинус bi-encoder, диапазон 0..1. Порог 3.0, применённый к косинусу, недостижим, и агент
уходит в «не знаю» на каждом ходу. Поэтому на `-backend local` порог переводится в
косинусную шкалу (0.35).

## RAG

Полный конвейер: индексация (`ragindex/`) → retrieval (`rerank.go`) → grounded-ответ
с цитатами (`cite.go`). Подробности формата — в `docs/index-format.md`.

Двухстадийный retrieval (`retrieveAdvanced`):

```
запрос → query rewrite → bi-encoder top-N → порог по косинусу → MMR → LLM-реранк → top-K
```

Grounded-ответ (`groundedReply`): модель обязана вернуть строгий JSON с полями `answer`,
`sources`, `quotes`. Каждая цитата проверяется КОДОМ по тексту поднятых чанков
(`verifyQuotes`) на трёх уровнях: `exact` (дословно), `partial` (по смыслу), пусто
(выдумана). Это анти-галлюцинационный контур: выдуманная цитата видна в отчёте.

Если лучший кандидат ниже порога — включается режим «не знаю»: ответ не генерируется вовсе.

## Локальные модели

`local.go` — `LocalLLM`, клиент Ollama на чистом `net/http` (без SDK): `/api/chat`,
`/api/generate`, `/api/tags`. Управляемые параметры: `Temp`, `NumPredict`, `NumCtx`.
Счётчики `LocalStats` (токены, время загрузки, время генерации) — основа всех замеров.

`serve30.go` — локальная модель как приватный HTTP-сервис, совместимый с OpenAI API:
`POST /v1/chat/completions`, `GET /v1/models`, `GET /health`. Bearer-ключ, token-bucket
rate-limit на IP, семафор конкурентности. Стриминг не поддержан (честный `400`).

## Ассистент разработчика (`help31.go`)

Команда `/help` соединяет два разных источника знания о проекте:

- **документация проекта** — через RAG (индекс `ragindex-docs`): «как устроено»;
- **контекст проекта** — через MCP-сервер `git`: «что происходит сейчас».

Гибридная схема получения git-контекста:

- **ветка и структура файлов** — детерминированным пре-фетчем: агент сам зовёт
  `git_branch` и `git_files` напрямую (`mcptools.Call`), не спрашивая модель. Ноль
  токенов, контекст гарантированно есть в каждом ответе, работает и на локальном бэкенде;
- **diff и история** — остаются тулами в обычном tool-use цикле: модель зовёт `git_diff`
  и `git_log` сама, когда вопрос того требует. Пре-фетчить diff нельзя — он может быть
  на десятки килобайт.

Контекст проекта не является источником для цитирования: у него нет `chunk_id`, это
состояние мира, а не документ. Он подмешивается в промпт отдельным блоком и не участвует
в верификации цитат.
