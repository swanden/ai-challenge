Тридцать второй день, и снова накопительный агент: каталог `week-7/task-32/` — это копия
вчерашнего `task-31/` с одной новой возможностью. В этот раз я сделал автоматическое ревью
кода, которое срабатывает само на новый pull request: агент берёт изменения (diff), сверяет их
с документацией и кодом проекта через RAG и оставляет текст ревью комментарием прямо в PR.
Заодно я закрыл долг, который остался с прошлого дня, — проблему «самоотравления» корпуса,
о ней подробнее ниже.

## Что говорит курс (разбор чата)

Несколько реплик из обсуждения в чате напрямую повлияли на то, как я построил решение.

Главное требование — реактивность. Автор курса подчёркивал, что ревью должно запускаться само,
на событие, а не по ручной команде: на прямой вопрос «а можно запускать командой?» он ответил
«нет». Возвращать результат он предложил комментариями прямо в pull request — «он может прям в
гитхаб возвращать, в виде комментов». При этом платформа не обязательно GitHub: подойдёт любой
сервис управления кодом.

Отдельно обсуждали, нужно ли хостить свой сервис, к которому будет обращаться CI. Автор сказал,
что можно, если хочется, — через reverse-proxy, ngrok или cloudflare tunnel. Я пошёл другим,
более простым путём, без всякого хостинга: ревьюер запускается прямо внутри временной машины CI.
Об этом — в разделе «Решение».

Ещё один важный момент касался нашего вчерашнего долга. Один из участников спросил, нормально ли,
что поисковый индекс RAG собирается заново при каждом запуске, и автор согласился, что это
избыточно; в идеале индекс строится один раз, а дальше обновляется по расписанию или вручную.
Это ровно та проблема, которую я оставил недоделанной в дне 31, и здесь я её закрыл.

Наконец, ещё один участник (Гаврись) заметил, что задание слабо связано с самим ассистентом и не
использует наши наработки. У меня связь есть: ревьюер — это режим того же самого агента, он
работает на том же корпусе и тех же серверах, что и команда `/help` дня 31, и при желании
запустится на локальной модели.

## Решение и альтернативы

### 1. Реактивность: ревьюер работает внутри самой машины CI

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| **Внутри GitHub-раннера** | не нужен ни хостинг, ни туннель; комментарий постится через встроенный токен `GITHUB_TOKEN`; для видео это один экран браузера | ключ `ANTHROPIC_API_KEY` кладётся в secrets (обычная практика для CI); Ollama поднимается в раннере | **выбрано** |
| Action обращается к моему сервису через ngrok / cloudflare | «настоящий» отдельный сервис | нужен живой хостинг и туннель, который прямо во время записи может отвалиться | отклонено |
| GitLab CI | тоже засчитывается | наш репозиторий (он же корпус) лежит на GitHub, а не на GitLab | отклонено |

### 2. Ревьюер — это режим нашего агента, а не отдельный скрипт

Я не стал писать ревью отдельным скриптом. Вместо этого ревьюер переиспользует уже отлаженный
поисковый конвейер `retrieveAdvanced` (переписывание запроса, поиск по эмбеддингам, отсев по
порогу, разнообразие MMR, переранжирование моделью) и общий механизм генерации `Completer`,
который умеет работать и с облаком, и с локальной моделью. Именно это делает решение цельным и
отвечает на претензию Гаврися.

Почему вообще нужен RAG, а не «просто отдай diff модели»: diff показывает, *что* изменилось, но
ничего не говорит о том, *как в этом проекте принято* писать. Ценность даёт именно контекст —
конвенции из документации, соседний код, который затрагивают изменения. Поэтому под каждый
изменённый файл ревьюер строит отдельный запрос к корпусу и подмешивает найденное в ревью.

### 3. Долг дня 31 закрыт: корпус больше не отравляет сам себя

В дне 31 я обнаружил (это была находка № 10), что мой рабочий журнал, живший прямо внутри README,
разросся примерно до 40% всего корпуса и начал вытеснять настоящую документацию из результатов
поиска. Здесь я это исправил двумя действиями. Во-первых, вынес журнал в отдельный файл
`docs/devlog.md` и запретил его индексировать — за это отвечает функция `skipFiles()` в
индексаторе. Во-вторых, сделал так, чтобы индекс переиспользовался: в CI он собирается заново
только если ещё не был закоммичен, а не каждый раз.

Здесь есть честный компромисс, о котором стоит сказать прямо: закоммиченный индекс со временем
устаревает по мере правок кода. Для нашего масштаба (около 50 файлов) это лечится ручным
пересбором, для больших репозиториев — сборкой по расписанию.

## Схема

```mermaid
flowchart TD
    PR["событие pull_request<br/>opened / synchronize"] --> WF[".github/workflows/ai-review.yml"]
    WF --> CO["checkout + git diff base…head → pr.diff"]
    CO --> OLL["Ollama: nomic-embed-text"]
    OLL --> IDX{"индекс закоммичен?"}
    IDX -- да --> REUSE["переиспользовать ragindex-docs"]
    IDX -- нет --> BUILD["собрать одноразово"]
    REUSE --> RUN
    BUILD --> RUN

    RUN["go run . -review-ci -diff-file pr.diff"] --> PARSE["parseDiff → FileDiff[]"]
    PARSE --> RAG["под каждый файл: retrieveAdvanced по корпусу"]
    RAG --> LLM["Completer: промпт ревьюера → строгий JSON"]
    LLM --> JSON["Review: Summary + Findings по severity"]
    JSON --> MD["renderReviewMarkdown"]
    MD --> POST["POST issues/{n}/comments (GITHUB_TOKEN)"]
    POST --> CMT["коммент в PR"]

    JSON --> GATE{"-review-strict И есть bug/architecture?"}
    GATE -- да --> FAIL["exit 1 — блокировать мёрж"]
```

### Шаг 0. Какие модели поднять и зачем

В этом дне участвуют две модели, и у них разные роли — их важно не перепутать.

| Роль | Модель | Как «запускается» | Нужно поднимать вручную? |
|---|---|---|---|
| Пишет само ревью | Claude (облако) | сама, при обращении к API | нет — достаточно ключа `ANTHROPIC_API_KEY` |
| Считает эмбеддинги для поиска | `nomic-embed-text` (Ollama, локально) | командой `ollama serve` | **да** |

Иными словами, «поднять модель» здесь означает запустить локальную модель эмбеддингов. Полноценную
генерирующую локальную модель (`qwen2.5:7b`) для дня 32 поднимать не нужно — ревью по умолчанию
пишет облачный Claude.

```bash
# 1. Облачная модель (пишет ревью): достаточно ключа в окружении
export ANTHROPIC_API_KEY=sk-ant-...
#    (или положить его в файл .env в корне репозитория)

# 2. Локальная модель эмбеддингов (для поиска по корпусу): поднять Ollama
ollama serve &                       # запустить сервер Ollama, если ещё не запущен
ollama pull nomic-embed-text         # скачать модель эмбеддингов
curl -s localhost:11434/api/tags | grep nomic   # убедиться, что модель на месте
```

Если хочется прогнать ревьюер полностью локально, без облака, то понадобится и генерирующая
модель, и флаг `-backend local`. Я это не проверял: строгий JSON, который мы требуем от ревьюера,
на модели 7B может получаться нестабильно.

```bash
ollama pull qwen2.5:7b
go run ./week-7/task-32 -review32 -diff-file /tmp/pr.diff -backend local -local-model qwen2.5:7b
```

## Сценарий A — одна команда для видео (в терминале, без озвучки)

Есть команда, которая сама себя объясняет: она берёт встроенный образец кода с типовыми
проблемами и печатает весь процесс по шагам — разбор diff, подключение контекста проекта,
найденные замечания и итоговый вердикт по блокерам.

Подготовка (один раз):

```bash
cd ~/projects/ai-challenge

# модель эмбеддингов для поиска
ollama serve &
ollama pull nomic-embed-text

# ключ облачной модели, которая пишет ревью
export ANTHROPIC_API_KEY=sk-ant-...

# собрать индекс по документации и коду проекта
go run ./week-7/task-32/ragindex -out week-7/task-32/ragindex-docs -ext .md,.go
```

Сама запись — одна команда:

```bash
go run ./week-7/task-32 -review-demo
```

На экране по порядку появятся: какой код ревьюируется, как подключается контекст проекта,
найденные проблемы, разбитые по важности (🔴 баги, 🟠 архитектура, 🟡 рекомендации), и итоговый
вердикт — есть ли блокеры для CI. Достаточно записать один прогон этой команды.

Если нужен не встроенный образец, а свой diff, есть ещё два варианта:

```bash
# ревью конкретного diff из файла
git diff main...HEAD > /tmp/pr.diff
go run ./week-7/task-32 -review32 -diff-file /tmp/pr.diff

# ревью diff, поданного через stdin
git diff HEAD~1 | go run ./week-7/task-32 -review32
```

## Сценарий B — реактивный: создать PR и увидеть комментарий

Этот сценарий показывает именно то, что просил курс: создаёшь pull request, и комментарий от бота
появляется в нём сам.

### B0. Подготовка (один раз, до записи)

```bash
cd ~/projects/ai-challenge

# 1. положить workflow в стандартную папку GitHub Actions
mkdir -p .github/workflows
cp week-7/task-32/.github-workflows-ai-review.yml .github/workflows/ai-review.yml

# 2. собрать индекс, чтобы Action не строил его на каждом PR (эмбеддер должен быть поднят)
go run ./week-7/task-32/ragindex -out week-7/task-32/ragindex-docs -ext .md,.go

# 3. закоммитить всё в main
git add .github/ week-7/task-32/
git commit -m "day 32: AI review workflow"
git push origin main
```

После этого нужно создать секрет с ключом Claude. Это обязательный шаг — без него Action не
сработает, ревьюер просто не сможет обратиться к модели и получит ошибку авторизации.

1. Открыть репозиторий на github.com
2. **Settings** (вкладка репозитория, не настройки аккаунта)
3. Слева: **Secrets and variables → Actions**
4. **New repository secret**
5. **Name:** `ANTHROPIC_API_KEY` (ровно так — workflow ищет это имя)
6. **Secret:** твой ключ `sk-ant-...` → **Add secret**

Право бота оставлять комментарий уже прописано в самом workflow, менять ничего не нужно:

```yaml
permissions:
  contents: read
  pull-requests: write   # разрешает боту постить коммент в PR
```

> ⚠️ **Главная грабля.** Workflow должен оказаться в ветке `main` до того, как ты создашь PR.
> GitHub берёт определение Action из целевой ветки pull request, а не из ветки самого PR. Поэтому
> шаг 3 (push в main) обязательно идёт первым.

### B1. Создать PR с намеренно проблемным кодом

```bash
cd ~/projects/ai-challenge
git checkout -b test-review

# файл с типовыми проблемами (пароль в лог + SQL-инъекция)
cat > week-7/task-32/badcode.go <<'EOF'
package main

import "database/sql"

func BadLogin(db *sql.DB, user, pass string) {
	println("login user=" + user + " pass=" + pass)
	db.Query("SELECT * FROM users WHERE name='" + user + "'")
}
EOF

git add week-7/task-32/badcode.go
git commit -m "test: code for AI review"
git push origin test-review
```

Затем на GitHub нажать **Compare & pull request** (база `main`, ветка `test-review`) и создать PR.

### B2. Увидеть комментарий (главный кадр видео)

Открываешь вкладку **Actions** — там идёт запуск «AI Review (day 32)». Первый прогон занимает
пару минут, потому что раннер ставит Go и Ollama. Когда он закончится, возвращаешься в PR и внизу
видишь комментарий-ревью от бота с замечаниями, разбитыми по важности.

Долгую установку в Actions на видео можно перемотать или склеить. После записи тестовую ветку
можно удалить: `git push origin --delete test-review`. А чтобы Action вообще перестал срабатывать
на каждый PR, достаточно удалить файл `.github/workflows/ai-review.yml` из `main`.

### Ревью проблемного кода (`-review-demo`)

Команда `-review-demo` берёт встроенный образец `badcode.go` (пароль в логе и склейка строк в SQL)
и печатает весь процесс. Итоговое ревью получилось таким:

```
### 🔴 Потенциальные баги
- SQL-инъекция через конкатенацию строк → параметризованный запрос
- Логирование пароля в открытом виде → утечка чувствительных данных
- Игнорирование ошибки и утечка *sql.Rows (rows.Close() через defer) от db.Query

### 🟠 Архитектурные проблемы
- Функция логина не возвращает (result, error)

### 🟡 Рекомендации
- println вместо стандартного логгера проекта

Найдено замечаний: 5 (🔴 3 · 🟠 1 · 🟡 1) · блокеры: true · токены: вход 1724 · выход 789
```

Из этого прогона я вынес три вещи.

Первое: ревьюер нашёл больше, чем я специально закладывал в пример. Пароль в логе и SQL-инъекция
были очевидны, но про игнорируемую ошибку и незакрытый `*sql.Rows` (это утечка соединений из пула)
в моём образце не было явного намёка — ревьюер догадался сам, зная, как ведёт себя `db.Query`, и
даже предложил конкретное исправление через `defer rows.Close()`.

Второе: RAG связал вызов `println` с конвенцией проекта — что в проекте принято использовать
стандартный логгер. Обычный линтер такого не даст, потому что это замечание опирается на код
именно этого проекта, а не на общее правило.

Третье: все три уровня важности отработали, и функция `HasBlockers()` правильно вернула «есть
блокеры» (потому что среди замечаний есть баги и архитектурная проблема) — на этом держится строгий
режим для CI.

Была и забавная деталь: в контекст ревьюер подтянул фрагмент `reviewrun.go` с константой
`sampleBadDiff` и разделы README про ревью, то есть нашёл в проекте описание собственного тестового
образца. Это заодно подтверждает, что порог релевантности (см. «Найденные баги», п. 2) работает —
подтягивается родственное, а не случайное.

## Найденные баги (по ходу реальных прогонов)

### 1. Корпус удваивался: в индекс попадал каталог `task-32 2`

Первый прогон дал 100 файлов и 1337 фрагментов вместо ожидаемых пятидесяти, а в источниках ревью
всплыл путь `task-32 2/local26.go`. Причина оказалась в том, что Finder или IDE при копировании
каталога создаёт его дубликат с именем вроде `task-32 2` прямо внутри проекта, и индексатор
исправно засасывал его целиком — отсюда и удвоение.

Исправил это функцией `isDupDir` в `ragindex/corpus.go`: она отсекает каталоги, чьё имя выглядит
как «имя-пробел-число» (`task-32 2`, `ragcore 3`). Настоящих имён с таким шаблоном у нас нет,
так что ложных срабатываний не будет.

### 2. В комментарий попадал нерелевантный контекст

Для изолированного файла `badcode.go`, у которого в корпусе нет близкой родни, переранжирование
всё равно поднимало «лучшее из худшего» — и явно нерелевантный фрагмент (`local26.go`) утекал в
блок «Контекст из проекта» в комментарии. На качество ревью это не влияло (модель его
игнорировала, все баги нашлись по самому diff), но в комментарии это выглядело мусором и вдвое
раздувало входные токены — с 1368 до 623 после исправления.

Исправил порогом релевантности в функции `gatherReviewContext`: слабые результаты поиска больше не
идут в контекст. Порог зависит от того, включено ли переранжирование моделью (тогда шкала 0–10) или
нет (тогда косинусная близость 0–1) — это тот же урок про согласование шкал, что был в дне 27.

## Границы решения

Стоит честно перечислить, что здесь упрощено или ограничено.

В workflow ревью намеренно ограничено каталогом `week-7/task-32/`, чтобы Action не комментировал
изменения в чужих днях челленджа; для настоящего проекта это ограничение убирается. Ревью выдаётся
одним сводным комментарием, а не построчными замечаниями к конкретным строкам diff — задание
просит «текст ревью», и сводный комментарий это выполняет, а построчные замечания были бы
следующим шагом (для них нужен отдельный вызов API с позициями в diff). Строгий режим
(`-review-strict`), который заваливает проверку при наличии багов, по умолчанию выключен — чтобы
AI-ревью не блокировало мёрж из-за ложных срабатываний; включать его стоит осознанно. Наконец, diff
обрезается по лимиту в 12000 символов, чтобы очень большой PR не вытеснил контекст из окна модели;
при этом первыми идут файлы с наибольшим объёмом правок.

## Что дальше

Естественное развитие — построчные комментарии к конкретным строкам diff вместо одного сводного.
Ещё стоит сделать по-настоящему инкрементальную переиндексацию вместо нынешнего «собрать заново,
если индекса нет» — это и будет полным ответом на замечание про избыточность пересборки. И, если
понадобится, того же ревьюера можно подключить как инструмент в ассистента поддержки дня 33.

## Выводы

Первый вывод: ревью без контекста проекта — это просто линтер. Ценность AI-ревьюера не в том, что
он читает diff, а в том, что он знает конвенции именно этого проекта. Поэтому под каждый изменённый
файл идёт отдельный запрос к корпусу, а не «весь diff одним куском в промпт».

Второй: реактивность оказалась дешевле, чем кажется. Запуск внутри раннера убирает и хостинг, и
туннель, а токен для комментария GitHub выдаёт Action сам. В итоге вся «инфраструктура» — это один
файл workflow.

Третий: долг стоит отдавать там, где он сильнее всего мешает. Самоотравление корпуса из дня 31 било
бы по ревьюеру даже сильнее, чем по команде `/help`, — журнал чужих багов в выдаче ревьюера это
прямой шум. Поэтому я закрыл этот долг именно здесь, а не отложил на потом.
