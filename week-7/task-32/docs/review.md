# Автоматизация ревью кода (день 32)

Реактивный пайплайн: новый pull request → ассистент анализирует diff, опираясь на
документацию и код проекта (RAG) → публикует ревью комментом в PR.

## Конвейер

```
событие PR → diff (base…head) → parseDiff → RAG под каждый файл → LLM-ревьюер → JSON → markdown → коммент в PR
```

Пайплайн переиспользует retrieval-конвейер ассистента (`retrieveAdvanced`) и шов
генерации (`Completer`) — это не отдельный скрипт, а режим того же агента.

## Компоненты

### `reviewdiff.go` — разбор unified diff

`parseDiff(diff) []FileDiff` вытаскивает из патча факты: затронутые файлы, добавленные
и удалённые строки, признаки нового/удалённого файла, сырые ханки. Парсер намеренно
минимальный и устойчивый: неполный diff не роняет его.

### `review.go` — ядро ревьюера

`reviewPR(ctx, agent, retriever, diff, cfg) Review` — полный конвейер:

1. разобрать diff, отсортировать файлы по объёму изменений, ограничить `MaxFiles`;
2. под каждый изменённый файл построить точечный RAG-запрос («конвенции и связанный
   код для <path>» + добавленные строки) и собрать контекст из корпуса;
3. один вызов `Completer` с промптом ревьюера → строгий JSON;
4. распарсить в `Review{Summary, Findings[]}`.

Замечание (`ReviewFinding`) имеет `Severity`: `bug` (сломается/некорректно),
`architecture` (нарушение конвенции, структурная проблема) или `suggestion`
(улучшение, не блокер). `Review.HasBlockers()` истинно при наличии bug/architecture —
на этом строится строгий режим CI.

Почему RAG, а не «отдай diff модели»: diff показывает «что изменилось», но не «как в
этом проекте принято». Ценность даёт контекст — конвенции из `docs/`, смежный код.
Поэтому под каждый файл строится свой запрос к корпусу.

### `reviewrun.go` — связь с внешним миром

Два режима одного бинаря:

- `runReview32` — локальный/демо: diff из `-diff-file` или stdin, ревью в терминал;
- `runReviewCI` — реактивный: diff из события, ревью комментом в PR через
  `postPRComment` (GitHub REST API, `POST /repos/{repo}/issues/{n}/comments`).

Постинг использует `GITHUB_TOKEN`, который GitHub Action выдаёт автоматически —
своего хостинга не требуется.

### `.github/workflows/ai-review.yml` — реактивность

Триггер `pull_request` (`opened`/`synchronize`/`reopened`). Раннер делает checkout,
строит diff `base…head`, поднимает Ollama с эмбеддером, переиспользует предсобранный
индекс (или собирает одноразово, если его нет) и запускает `-review-ci`.

## Флаги

| Флаг | Смысл |
|---|---|
| `-review32` | локальное ревью diff'а в терминал (diff из `-diff-file` или stdin) |
| `-review-ci` | реактивный режим: ревью комментом в PR (нужны `GITHUB_*` env) |
| `-diff-file` | путь к файлу с unified diff (пусто = stdin) |
| `-review-strict` | exit 1 при наличии bug/architecture (блокировать мёрж) |
| `-review-dry` | не постить коммент, только напечатать |

## Связь с днём 31

Ревьюер использует тот же индекс `ragindex-docs` (документация + код), что и `/help`,
и тот же MCP `gitserver` (`git_diff` — для локального прогона). Долг дня 31 (не строить
индекс каждый раз, вынести рабочий журнал из корпуса) закрыт здесь: `devlog.md` не
индексируется, а индекс в CI переиспользуется, если закоммичен.
