# 🔥 День 10. Управление контекстом: разные стратегии (без summary)

## Задание

Реализуйте в агенте 3 разные стратегии управления контекстом (минимум) и переключатель между ними:

- 👉 **Стратегия 1 — Sliding Window:** храните только последние N сообщений, остальное отбрасывайте.
- 👉 **Стратегия 2 — Sticky Facts / Key-Value Memory:** отдельный блок `facts` (ключ→значение) с важными данными (цель, ограничения, предпочтения, решения, договорённости); обновляйте facts после каждого сообщения пользователя; в запрос — facts + последние N.
- 👉 **Стратегия 3 — Branching:** checkpoint в диалоге, 2 ветки от одного места, независимое продолжение, переключение между ветками.

Протестируйте на одном сценарии («собираем ТЗ за 10–15 сообщений»), прогоните на каждой стратегии, сравните: **качество ответа · стабильность (не теряет ли важные детали) · расход токенов · удобство.**

## Результат

Агент с 3 стратегиями (Sliding Window / Facts / Branching) + сравнение результатов.

## Архитектура: переключаемая стратегия

Контекст строит **стратегия**, а не сам агент. Интерфейс:

```go
type Strategy interface {
Name() string
Prepare(ctx, userInput) (system []TextBlockParam, msgs []MessageParam, err error)
Commit(assistant string)
}
```

`Prepare` принимает новое сообщение пользователя, обновляет состояние стратегии и
возвращает то, что реально уйдёт в модель. `Commit` сохраняет ответ. Агент дёргает
`Prepare → вызов модели → Commit` и не знает деталей. Переключатель — `agent.SetStrategy(...)`
или флаг `-strategy`.

### Стратегия 1 — Sliding Window

Буфер последних N сообщений; всё старше N отбрасывается (`lastN`). Просто и дёшево,
но к концу длинного диалога ранние детали **теряются** — окно их не видит.

### Стратегия 2 — Sticky Facts

`facts map[string]string` — key-value важных данных. После каждого сообщения
пользователя дешёвая модель (**Haiku**) обновляет facts (возвращает JSON ключ→значение,
парсится в map). В запрос идёт блок facts (system) + последние N сообщений. Окно
маленькое, но **важное не теряется** — оно в facts. Накладные — служебные вызовы
Haiku (учитываются отдельно).

### Стратегия 3 — Branching

`branches map[string][]message`, активная ветка `current`. `Branch(name)` форкает
текущую историю (checkpoint), `Switch(name)` переключает. Каждая ветка продолжается
**независимо** и помнит свой выбор. Не про экономию токенов — про параллельные
A/B-сценарии от общего начала.

## Два режима

### Отчёт — сравнение стратегий на сценарии «собираем ТЗ»

```bash
go run . -report
```

Прогоняет один сценарий (11 сообщений: стек, требования, дедлайн → «собери всё ТЗ»)
на Sliding Window и Sticky Facts, считает **стабильность** (сколько из 10 ключевых
фактов попало в финальное ТЗ) и токены, плюс показывает Branching-демо (2 ветки,
каждая помнит свою базу данных).

### Интерактивный чат с выбором стратегии

```bash
go run . -strategy facts       # sliding | facts | branching
```

Для Branching доступны команды чата: `/branch <имя>` — форк, `/switch <имя>` — переключить ветку.

## Сравнение по критериям задания

> По реальному прогону (числа в примере выше).

**Качество / стабильность — главное различие.** Sliding Window при окне N=4 теряет
ранний стек (order-svc, Postgres, Kafka вышли за окно) — **7/10** фактов. Важная
деталь: модель не выдумала потерянное, а честно пометила «не обсуждали → открытые
вопросы» — поведение хорошее, но ТЗ всё равно неполное. Sticky Facts держит всё в
`facts` и собирает ТЗ целиком — **10/10**.

**Расход токенов.** Итоговая стоимость почти целиком определяется **output**
(длиной ответов): у Sliding Window это ~**74%** суммы. Длину ответов стратегия
**не контролирует**, поэтому общий счёт сильно зависит от того, насколько развёрнуто
ответила модель. На этом прогоне Sticky Facts вышел и стабильнее, и дешевле
($0.314 vs $0.373); на другом — наоборот окно было чуть дешевле по input. Стабильный
вывод один: **стратегия управляет input и памятью, а итоговым счётом правит output** —
хочешь резать стоимость, ограничивай длину ответов (`MaxTokens`/просьба отвечать кратко).

**Удобство для пользователя.** Sliding Window — просто и предсказуемо, но забывчиво
на длинной задаче (и честно об этом сообщает). Sticky Facts — помнит главное при
коротком окне, идеально для сбора ТЗ. Branching — удобно вести A/B-варианты от общей
точки, не смешивая их.

**Итог:** «лучшей» стратегии нет. Короткий чат → Sliding Window; долгая задача с
важными фактами → Sticky Facts; исследование вариантов → Branching.

## Файлы

- `strategy.go` — интерфейс `Strategy` и три реализации (Sliding Window, Sticky Facts, Branching).
- `agent.go` — агент с переключаемой стратегией и учётом токенов (диалог + накладные).
- `usage.go` — тарифы по моделям, `costFor`, типы сообщений.
- `report.go` — сценарий «собираем ТЗ», проверка стабильности, Branching-демо, сравнение.
- `main.go` — флаги `-report` / `-strategy`, команды веток в чате.
