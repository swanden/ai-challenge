# 🔥 День 9. Управление контекстом: сжатие истории

## Задание

Реализуйте механизм управления контекстом:

- 👉 храните последние N сообщений «как есть»
- 👉 остальное заменяйте summary (например каждые 10 сообщений)
- 👉 храните summary отдельно и подставляйте его в запрос вместо полной истории

Сравните: качество ответов без сжатия / со сжатием · расход токенов до/после.

Агент, который работает с компрессией истории и экономит токены.

## Как устроено сжатие

Агент держит две вещи:

1. **`summary`** — конспект свёрнутой (старой) части диалога;
2. **`history`** — последние `keepLast` сообщений «как есть».

Когда сырых сообщений становится больше `keepLast + batch`, самые старые
сворачиваются в `summary`, а в буфере остаются последние `keepLast`. В запрос
уходит **не вся история**, а `summary` (как system-промпт) + последние сообщения.
В контекст сохраняются обе роли — и вопросы, и ответы.

**Сводки делает дешёвая модель.** Суммаризация не требует топ-модели, поэтому
конспект строит **Haiku 4.5 ($1/$5)**, а не Opus 4.8 ($5/$25) — в 5 раз дешевле
и по input, и по output. Это ключевой момент: без этого на среднем диалоге
сжатие легко уходит в минус (output сводок дорогой). Конспект ещё и тугой
(промпт требует краткости, без markdown), чтобы summary не раздувался.

`summary` хранится **отдельно** и персистится с сообщениями:

```json
{
  "summary": "Проект order-svc, язык Go, база Postgres, очередь Kafka. ...",
  "messages": [ { "role": "...", "content": "..." } ]
}
```

> Формат `history.json` изменился (объект `summary` + `messages`). Старый файл удалить.

## Два режима

```bash
go run . -report   # сравнение без/со сжатием (диалог 12 ходов)
go run .           # чат со сжатием (keepLast=6, batch=6)
```

В чате диалог идёт на Opus, сводки — на Haiku; в строке `[session]` стоимость
считается по тарифам обеих моделей.

## Как мы к этому пришли (эволюция `-report`)

Сжатие настраивалось итеративно — ниже ключевые прогоны (только итоговые цифры).
Хорошо видно, что сжатие само по себе денег не экономит: важно *как* его делать.

**Вариант 1 — 8 ходов, сводки на Opus, частое сжатие (keepLast=4, batch=4):**

```
• Без сжатия: Σinput=5415, стоимость $0.06270.
• Со сжатием: Σinput=6637, стоимость $0.08399 (2 сжатия, 2306 токенов сводок на Opus).
→ input +23%, стоимость +34% — сжатие ДОРОЖЕ полной истории.
```
Дорогой суммаризатор + частое сжатие на коротком диалоге = чистый убыток.

**Вариант 2 — 12 ходов, сводки на Opus, тугой конспект (keepLast=4, batch=6):**

```
• Без сжатия: Σinput=10374, стоимость $0.09187.
• Со сжатием: Σinput=9890, стоимость $0.10525 (2 сжатия, 2423 токенов сводок на Opus).
→ input −5%, стоимость +15% — контекст чуть ужался, но дорогой output сводок всё съел.
```
Стало понятно, что проблема — в дорогом суммаризаторе, а не в самой идее.

**Вариант 3 — 12 ходов, сводки на Haiku (keepLast=4, batch=6) ← текущий:**

```
• Без сжатия: Σinput=8491, стоимость $0.07343.
• Со сжатием: Σinput=7417, стоимость $0.06460.
    накладные на сводки (Haiku): 1354 input + 396 output = $0.00333.
→ input (всего) −13%, input (только диалог) −29%, стоимость −12% — сжатие ВЫГОДНО.
```
Дешёвый суммаризатор + раздельный учёт по моделям → реальная экономия без потери фактов.

## Выводы по задаче

### 1. Расход токенов до/после

- Без сжатия каждый ход пересылает **всю** историю, поэтому `Σinput` растёт
  квадратично по числу ходов. Это и есть главный источник расходов в длинном диалоге.
- Со сжатием в запрос идёт `summary` + последние `keepLast` сообщений, и контекст
  одного хода держится почти постоянным → `Σinput` растёт линейно.
- В реальном прогоне: контекст «чистого» диалога ужался на **−29%**, общий
  `Σinput` (со сводками) — на **−13%**, стоимость — на **−12%**. Отчёт показывает обе цифры плюс накладные на сводки,
  чтобы было видно, **куда** уходят токены.

### 2. Сжатие — компромисс, а не бесплатная экономия

- Сводка — это **дополнительный вызов модели** со своими input- и output-токенами.
  Она не уменьшает расход «сама по себе», а переносит его: меньше контекста в
  каждом ходе, но плюс периодические summary-вызовы.
- **Output дороже input в 5 раз.** Сводка генерирует output, поэтому её стоимость
  определяется в основном выходными токенами. Это легко делает наивное сжатие
  убыточным.
- Замеры это подтвердили: на первых прогонах (сводки на Opus, частое сжатие)
  выходило **input −5%, но стоимость +15%** — сжатие стоило дороже полной истории.
- После перехода на Haiku-сводки и более редкого сжатия тот же по структуре
  диалог дал **стоимость −12%** (реальный прогон выше) — сжатие стало выгодным.

### 3. Что делает сжатие выгодным

- **Дешёвая модель для сводок.** Суммаризация не требует топ-модели: конспект
  строит **Haiku 4.5 ($1/$5)** вместо Opus 4.8 ($5/$25) — в 5 раз дешевле и по
  input, и по output. Это решающий рычаг.
- **Тугой конспект.** Промпт суммаризатора требует краткости, без markdown,
  таблиц и списков, с лимитом длины — иначе `summary` раздувается и заменяет
  «много истории» на «почти столько же summary».
- **Реже сжимать.** Чем больше `batch`, тем реже summary-вызовы и меньше накладных
  (ценой чуть большего сырого буфера).
- **Стоимость считать по каждой модели отдельно** (Opus для диалога, Haiku для
  сводок) — иначе цифры врут.

### 4. Точка окупаемости

- Выгода сжатия растёт с длиной диалога: экономия на контексте квадратична, а
  стоимость сводок — фиксированная. На **коротком** диалоге сводки не успевают
  окупиться. Поэтому отчёт считает разницу **со знаком** и честно пишет, если
  сжатие не окупилось.

### 5. Качество ответов

- Контрольный вопрос в конце проверяет, пережили ли факты компрессию. К этому
  моменту исходные сообщения уже свёрнуты в `summary` и в сыром буфере их нет —
  но агент отвечает верно. Значит сжатие **сохраняет суть**, а не просто обрезает
  историю.
- Риск сжатия — потеря деталей, не попавших в конспект. Снижается тем, что промпт
  сводки явно требует сохранять факты, имена, числа, решения и открытые вопросы.

### 6. Детали реализации, влияющие на корректность

- В контекст (и в `summary`) сохраняются **обе роли** — вопросы пользователя и
  ответы модели; иначе модель не «помнила» бы собственных реплик.
- Служебный вызов суммаризации **не** попадает в историю — иначе конспект начал бы
  ссылаться сам на себя.
- `summary` хранится **отдельно** от сообщений и персистится вместе с ними
  (`State{Summary, Messages}`), так что контекст переживает перезапуск.
