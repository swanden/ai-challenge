# День 20. Orchestration MCP

Накопительно от дня 19. Агент подключается к **двум MCP-серверам разной природы**,
агрегирует их инструменты и **маршрутизирует** каждый вызов к серверу-владельцу. LLM сам
выбирает нужный тул и порядок, выполняя длинный кросс-серверный флоу.

```
            ┌─────────────── агент (один tool-use цикл) ───────────────┐
            │   маршрутизация по имени тула → нужный сервер             │
            └───────────────┬───────────────────────┬──────────────────┘
                  weather-сервер                 notes-сервер
        (geocode, weather_collect,          (save_to_file, read_file,
         make_report, track_location, …)     list_files, delete_file)
```

## Архитектура: два сервера + маршрутизация

Разбили по природе тулов на два независимых stdio-сервера:

| Сервер | Природа | Тулы |
|---|---|---|
| `weatherserver` | источник данных (погода) | `geocode`, `weather_current`, `weather_collect`, `make_report`, `track_location`, `weather_summary`, `list_tracked`, `untrack_location` |
| `notesserver` | хранилище файлов | `save_to_file`, `read_file`, `list_files`, `delete_file` |

Агент при старте поднимает **оба** сервера (каждый — свой сабпроцесс по stdio), собирает
их `tools/list` в общий список для модели и строит таблицу маршрутизации
**имя тула → сессия сервера-владельца**. Когда модель просит тул, `MCPTools.Call`
направляет вызов в нужный сервер:

```go
func (m *MCPTools) Call(ctx, name, input) (string, bool) {
session, ok := m.route[name]   // ← маршрутизация по имени тула
if !ok { return "неизвестный инструмент: " + name, true }
res, err := session.CallTool(ctx, &mcp.CallToolParams{Name: name, Arguments: args})
...
}
```

Модель видит единый плоский список тулов и не знает про границы серверов — выбор и
порядок вызовов она строит сама (как в дне 19), а агент лишь разводит вызовы по серверам.

## Длинный кросс-серверный флоу

Запрос пользователя (одной фразой) задействует тулы **обоих** серверов:

> «Собери погоду в Берлине, Софии, Париже и Лондоне, сделай сводный отчёт, сохрани в
> trip.txt, затем прочитай файл и скажи, в каком городе теплее».

```mermaid
sequenceDiagram
    participant U as Пользователь
    participant A as Агент (маршрутизатор)
    participant L as LLM
    participant W as weatherserver
    participant N as notesserver
    U->>A: длинный запрос (1 фраза)
    L-->>A: weather_collect(4 города)
    A->>W: → weather-сервер
    W-->>A: {"cities":[...]}
    L-->>A: make_report(cities)
    A->>W: → weather-сервер
    W-->>A: текст отчёта
    L-->>A: save_to_file(trip.txt, отчёт)
    A->>N: → notes-сервер
    N-->>A: сохранено: notes/trip.txt
    L-->>A: read_file(trip.txt)
    A->>N: → notes-сервер
    N-->>A: содержимое файла
    L-->>A: финальный ответ
    A-->>U: «Теплее всего в Софии; отчёт в notes/trip.txt»
```

Здесь видно и **выбор** нужного тула, и **маршрутизацию** (`weather_collect`/`make_report`
→ weather, `save_to_file`/`read_file` → notes), и **порядок** (collect → report → save → read).

## Из лекции (по теме задания)

Отдельной лекции по дню 20 не было — есть вводная лекция MCP на неделю
(`MCP-intro-konspekt.md`). Релевантные дню 20 (оркестрация) места из неё:

**Цель недели (§9 конспекта) — день 20 её и закрывает:**
- Научиться **оркестрировать MCP в своём агенте**: когда тулов много и запрос большой,
  агент должен сам выбирать нужные и комбинировать. День 20 — кульминация: тулы приходят
  уже с нескольких серверов, а выбор/порядок строит модель.
- Реализовать MCP для **публичных** тулзов — поэтому в задании допустимы и сторонние серверы.

**Токеновая экономика (§8) — почему «3–4 MCP» это не бесплатно:**
- MCP при каждом sampling-call заново кладёт в контекст **схемы всех тулов** со всех
  подключённых серверов; расход **растёт квадратично** (в примере лекции ~20 экшенов →
  ~59927 токенов против ~15846 у Skill+CLI), плюс **idle-расход** (~5787) просто за факт
  подключения. Чем больше серверов/тулов оркеструешь — тем тяжелее каждый вызов.
- Прямой вывод для дня 20: «упороться в 3–4 MCP» полезно для инсайта, но в проде это
  цена в токенах. Отсюда практики: не держать лишние серверы подключёнными, дробить по
  природе (как у нас weather/notes) и не плодить тулы без нужды.

**Где MCP нужен (§1) — почему естественно иметь несколько серверов:**
- Разные системы (таск-трекер, база знаний, календарь, DevOps) — это и есть разные MCP.
  Длинный флоу «собрал из одного источника → обработал → сохранил в другой» ложится на
  несколько серверов разной природы (ровно наш weather → notes).

**MCP vs API (§2):** MCP — это стандарт, а не фреймворк: единый протокол позволяет агенту
ровно так же подключать и оркестрировать чужие серверы, как свои — что и проверяет день 20.

## Ленивая загрузка схем тулов (экономия токенов)

### Откуда это
Из обсуждения в чате потока (Георгий ↔ Алексей) и токеновой экономики вводной лекции:

- Алексей: при работе с MCP модель **каждый раз тянет всю схему инструментов**, чтобы
  выбрать подходящий. Если свалить всё в один сервер — расход растёт «×100» за каждый
  запрос списка тулов. Экономия возможна, если грузить **не все схемы сразу**: сначала
  модель видит каталог серверов, понимает, что задача про notion → запрашивает тулы
  только notion (`notion__mcp_get_list`), и лишь потом дёргает конкретный тул.
- Георгий поймал ключевое (вывод его Клода): **само по себе разделение на серверы экономию
  НЕ даёт** — экономит **маршрутизация по схемам** (ленивая загрузка тулов нужного сервера).
  «Разделил на сервера, а передавал весь лист тулзов» → экономии не видно.

То есть базовый день 20 (все 12 тулов в каждый запрос) даёт правильную маршрутизацию
*вызовов*, но не экономит токены: схемы обоих серверов уходят в модель всегда. Этот шаг
исправляет именно это.

### Что это
Ленивая (отложенная) загрузка схем по серверам. Модель стартует не с полным списком
тулов, а с **каталогом серверов** + один мета-тул `load_tools`. Полная схема тулов сервера
подмешивается в запрос, **только когда модель сама её запросила** под конкретную задачу.

### Как работает
```
старт: модель видит ТОЛЬКО каталог:
   load_tools(server) — "weather — погода/геокодинг/слежение (тулов: 8);
                          notes — файловое хранилище (тулов: 4)"
        │
   модель: load_tools(server="weather")     ← поняла, что задача про погоду
        │  агент подмешивает 8 схем weather в params.Tools
   модель: weather_collect(...) → make_report(...)
        │
   (если нужно сохранить) load_tools(server="notes")
        │  агент подмешивает 4 схемы notes
   модель: save_to_file(...) → read_file(...)
```
Для задачи, которой нужен только weather, **схемы notes в модель не уходят вообще** — вот
и экономия. Чем больше серверов/тулов в системе, тем сильнее эффект.

### Как реализовано
- `MCPTools.CatalogTools()` — стартовый набор: один мета-тул `load_tools` с enum серверов;
  в описании — имена и назначение серверов (дёшево), но БЕЗ полных схем их тулов.
- `MCPTools.LoadServer(server)` — отдаёт схемы тулов запрошенного сервера + текст-подтверждение.
- `agent.go`: в ленивом режиме старт с `CatalogTools()`; когда модель зовёт `load_tools`,
  агент перехватывает это **сам** (не маршрутизирует на сервер), подмешивает схемы через
  `appendNewTools` (с дедупом) в `params.Tools` следующих раундов и возвращает модели,
  какие тулы теперь доступны. Реальные тулы по-прежнему идут через инварианты и `route`.
- `main.go`: флаг `-lazy` (по умолчанию `true`). `-lazy=false` — прежнее жадное поведение.

Мета-тул `load_tools` обрабатывается агентом и **не** требует MCP-вызова и не входит в
маршрутизацию; через инварианты он не гоняется (это не действие, а загрузка схемы).

### Как увидеть экономию (для видео)
`Reply` суммирует входные токены по всем раундам. Сравни один и тот же **однострочный
запрос про один сервер** в двух режимах:
```bash
go run ./week-4/task-20 -lazy=false   # жадный: в модель уходят схемы ОБОИХ серверов
> какая сейчас погода в Берлине?
go run ./week-4/task-20 -lazy=true    # ленивый: уходит только каталог + схемы weather
> какая сейчас погода в Берлине?
```
В ленивом режиме схемы `notes` не отправляются → входных токенов меньше. На длинном
кросс-серверном флоу (collect→report→save→read) оба сервера всё равно загрузятся —
экономия **зависит от задачи**, и это нормально: платим схемой только за то, что реально нужно.

> Несколько MCP-серверов на одном VPS/машине — нормально (подтвердили в чате Георгий и
> Andrey: «три mcp и сама llm на одной машине»). Разделение — про организацию и
> маршрутизацию схем, а не про физические машины.

## Проверка критериев

- **Несколько MCP-серверов** — `weather` и `notes`, оба поднимаются агентом.
- **Агент выбирает нужный инструмент** — единый список тулов, выбор делает LLM.
- **Корректная маршрутизация** — `route[имя]→сессия`; вызов идёт на сервер-владельца.
- **Длинный флоу** — collect → report → save → read (4 вызова, 2 сервера) по одной фразе.
- **Инструменты с разных серверов в одном сценарии** — weather-тулы + notes-тулы вместе.

## Как дотянуть до 3–4 серверов (по желанию куратора)

Добавить ещё `ServerSpec` в `servers` в `main.go` — напр. сторонний
`npx -y @modelcontextprotocol/server-filesystem /tmp` или `uvx mcp-server-time`.
`ConnectMCP` подхватит их тулы и сам добавит в маршрутизацию — код агента не меняется.
